## 1. What this is

Tile RPG is a calm, mobile-first card-collecting town game. You walk around a tile map, meet neighbours, battle with a 12-card deck, collect cards, fish, garden, cook, decorate, and so on. It's in a **playtesting phase** with a small group of testers.

- **`index.html` is the real game**, split across plain files with **no build step** and one vendored library, PixiJS (`assets/vendor/pixi.min.js`, build 134; everything else is plain files, and the game still works without it through the classic DOM town) (as of v1.15.0's file split - see §4):
  - `index.html` - the HTML shell (head, all the panel/overlay markup) plus a `<script src>` for each JS file below, loaded **in this exact order**.
  - `css/*.css` - all CSS, one stylesheet cut into six files in cascade order (`base`, `screens`, `battle-town`, `buildings`, `battle-v2`, `latest`; index.html links them in that order and a later file overrides an earlier one). **Append new rules to `latest.css`.** Every colour lives in `css/theme.css` (build 253), linked before the six: its palette (`--c-<hue>-<lightness>`) and all colour tokens (`:root`, `:root[data-theme="light"]`, biome palettes on `.town-view[data-biome=…]`, seasonal foliage on `[data-season=…]`, building and battle palettes). The six files only read them with `var()`.)
  - `assets/sprites.js` - every game icon as an inline SVG `<symbol>`, written into the document via `document.write()` from a plain `<script src>` at the spot the markup used to hold them inline. **This is deliberate, not a workaround to remove**: Chromium does not support `<use href="external.svg#id">` (cross-document SVG sprite references), only same-document `#id` fragments, and `fetch()`/XHR of a local file is blocked by CORS when the game is opened via `file://`. `document.write` from a script tag is the one technique that gets external-file editability *and* keeps the symbols in the same document *and* keeps working when someone just double-clicks the file. **To swap in your own art:** edit this file, keep the same `id`s (`s-oak`, `b-cottage`, `p-fountain`, …), and nothing else needs to change.
  - `js/*.js` - ~22 files, one per subsystem (see §4's table for exactly which). All classic `<script>` tags, **not** ES modules - `type="module"` blocks `file://` testing (browsers refuse cross-origin module loads from the filesystem), so everything shares one global scope via plain script tags, same as if it were still one file.
  - `manifest.json` / `sw.js` / `assets/icon-*.png` - makes the game an installable, fully offline-capable PWA (added post-v1.15.0; see the new §1a below). The icons are a placeholder (a card emoji on a green square) until the owner's own art replaces them.
- **`Tile RPG.html`** now just forwards to `index.html` (this is the reverse of before v1.15.0's split, when `index.html` forwarded to `Tile RPG.html`) - kept so old bookmarks/links to that filename still work.
- To run it, open `index.html` in a browser. For a phone-sized view, use a 400×860 viewport.

### 1a. Offline support (PWA) and the plan for cloud saves

- **Offline is done.** `sw.js` precaches every same-origin file that `index.html` and `manifest.json` themselves reference (parsed out of those two files at install time, not hand-listed in `sw.js`) via the Cache API (cache-first, falling back to network for anything not precached). Add a new `<script>`/`<link>` to `index.html` and it's automatically precached next publish - nothing to update in `sw.js` itself beyond bumping `BUILD`. `manifest.json` makes it installable. Test this specifically with an actual HTTP server, not `file://` - service workers require a secure context and silently refuse to register under `file://` (the registration in `index.html` is wrapped in `.catch(() => {})` for exactly this reason, so normal `file://` testing is unaffected, it just never gets a service worker). A one-line static server for this: `node -e "require('http').createServer((q,r)=>require('fs').readFile('.'+decodeURIComponent(q.url.split('?')[0])||'./index.html',(e,d)=>{r.writeHead(e?404:200);r.end(d||'404');})).listen(8123)"`, then point Playwright/a browser at `http://localhost:8123/`. Note that server sends no `Content-Type` header, which is enough to make Chrome refuse to register a service worker (wrong MIME type) - fine for everything else, but if you're specifically testing SW/update behavior, serve `.js` as `application/javascript` and `.html`/`.css`/`.json` with their real types too.
- `sw.js` builds its `CACHE_VERSION` from `BUILD` in `js/build.js` (`importScripts('js/build.js')`); bump `BUILD` by one on every publish - see the publish checklist in §2, which is the canonical place this is documented. It's independent of the game's own version number, and also gets bumped for internal-only changes that add nothing to `PENDING_CHANGES`.
- **Precache bypasses the HTTP cache** (`cache: 'reload'` in `sw.js`'s install step). GitHub Pages serves files with `max-age=600`, so a plain `cache.addAll()` could precache the *previous* publish's CSS/JS on a phone that had loaded them in the last ten minutes - the new service worker "installed" but the player still saw old screens (this made a Card Shop layout fix look like it hadn't shipped). If a fix seems not to appear on a real device, first check the version label (profile menu / Journal) before assuming the code is wrong.
- **Settings -> Update game (build 171, `forceUpdateGame` in `index.html`).** A forced refresh for a phone stuck on an old copy: unregisters the service worker, deletes every Cache Storage entry, re-fetches `index.html` and every local script / stylesheet / `sw.js` / `manifest.json` with `cache: 'reload'` (GitHub Pages' `max-age=600` could otherwise hand the reload the old files), then reloads. Never touches `localStorage` or the cloud save. `reload` is a parameter so `tests/force-update.test.js` can watch it (Chromium will not let a test stub `location.reload`).
- The page also actively checks for a newer `sw.js` (on becoming visible, and hourly) and shows a "new version ready" banner (`#updateBanner` in `index.html`) rather than relying only on the browser's own infrequent background check - added because Android home-screen shortcuts in particular could stay stuck on an old cached version for a long time otherwise.
- **Cloud saves are done (v1.17.0), in `js/cloud-save.js`.** `localStorage` stays the fast, always-available, offline-first save (nothing in `loadState()`'s own logic changed); Firestore is a background backup layered on top, using the Firebase **compat** SDK (`firebase-app-compat.js` / `firebase-auth-compat.js` / `firebase-firestore-compat.js`, loaded from `gstatic.com` - **not** the modular v9+ SDK, which is ES-module-only and would break `file://` testing the same way `type="module"` scripts do).
  - **Loaded last, deliberately.** The three Firebase `<script>` tags and `js/cloud-save.js` sit at the very end of `index.html`, after every game file - so a slow or unreachable connection to Google's CDN can never delay the game itself loading and rendering from the local save. `cloud-save.js` calls its own `cloudInit()` at the bottom of the file, rather than being kicked off from the game's own start-up sequence, for the same reason.
  - **Auth is anonymous by default** - a hidden account is created on first play, no login screen. `saveState()` (in `js/progression.js`) calls `cloudSaveDebounced()` after every local save, which coalesces bursts into one Firestore write every `CLOUD_SAVE_DEBOUNCE_MS` (currently 8s) - `saveState()` is called very often, and the Firestore free tier has a daily write quota. On sign-in (including the very first one), `cloudPullThenReconcile()` compares the cloud copy's `savedAt` against the local `state.cloudSavedAt` and takes whichever is newer - "last write wins," no field-level merge. This is a deliberately simple policy for a casual game in playtesting; revisit if it ever causes a real complaint.
  - **"Back up your save" / "Restore a save"** (Settings, next to Comfort settings) link or sign into an email + password on top of the same hidden anonymous account (`linkWithCredential` / `signInWithEmailAndPassword`), using `prompt()` for the two text inputs - deliberately the simplest possible UI for a first cut, not a polished modal. Restoring always takes the cloud copy unconditionally (the player just said which save they want), everything else uses the timestamp comparison above.
  - **Everything in this file checks `typeof firebase !== 'undefined'` and no-ops if it's missing**, so a blocked/unreachable CDN, or a genuinely offline player, degrades to "exactly like before this file existed" rather than breaking anything. This is also why `sw.js` does **not** precache the three Firebase CDN scripts (cross-origin, and pointless to cache something that's useless without a live connection anyway) - only `js/cloud-save.js` itself.
  - **Firestore security rules** (paste into the Firebase console → Firestore → Rules): one document per user, keyed by their auth `uid`, readable/writable only by that same authenticated user:
    ```
    rules_version = '2';
    service cloud.firestore {
      match /databases/{database}/documents {
        match /saves/{uid} {
          allow read, write: if request.auth != null && request.auth.uid == uid;
        }
      }
    }
    ```
  - **This was built and tested from a sandbox with `gstatic.com`/`googleapis.com` blocked by its own network policy** (an environment-level restriction on that Claude session, unrelated to real players' browsers) - confirmed the graceful no-op path works perfectly (all Playwright smoke tests pass with the Firebase scripts failing to load), but couldn't exercise a live sign-in/read/write from that sandbox itself. **The owner has since verified it live**: `cloudStatus` in Settings shows "Backed up automatically", a `saves/<uid>` document appears in the Firestore console after playing, and the full backup → restore-on-another-device loop works.
  - **"Back up"/"Restore" open a real modal** (`#cloudOverlay` in `index.html`, wired in `js/cloud-save.js`'s `cloudOpenModal`/`cloudCloseModal`), not `prompt()` - added in v1.18.0 once the underlying sync was confirmed working live. It sits at `z-index: 55` since it's opened from inside the player menu (`z-index: 50`) - see the overlay-stacking gotcha below if adding another overlay that can open from inside another one.
  - **"Who's Playing" (v1.40.0) needs a second Firestore rule the owner still has to paste in** - a low-pressure, opt-in glance at the other testers (name, level, district, last seen), deliberately not a leaderboard, in a separate `players` collection since (unlike `saves`) every signed-in tester needs to *read* everyone's entry, not just their own:
    ```
    match /players/{uid} {
      allow read: if request.auth != null;
      allow write: if request.auth != null && request.auth.uid == uid;
    }
    ```
    Add this alongside the existing `saves` rule (same `rules_version = '2'` block). Off by default and its own toggle (`prefs.sharePresence`, separate from cloud save itself) - sharing your name/activity with other testers is a different call than just backing up your own save privately. Until this rule is added, `pushPresence()`/`fetchWhosPlaying()` in `js/cloud-save.js` just fail silently like any other unreachable-Firestore case - **this was built and tested the same way as the original cloud save rule above (sandbox network blocked, so only the graceful-failure path was actually exercised) and needs the same live verification once the rule is in place.**
  - **Feedback/bug reports need a third Firestore rule** - `sendFeedback()` (js/events-story-foils-guide.js) now writes straight to a `feedback` collection via `pushFeedback()` (js/cloud-save.js) instead of opening a `mailto:` link, so it needs its own **write-only** rule (nobody, not even the submitting player, ever reads it back through the app - only the owner does, from the Firebase console):
    ```
    match /feedback/{doc} {
      allow create: if request.auth != null;
      allow read, update, delete: if false;
    }
    ```
    Add this alongside the existing `saves`/`players` rules. Until it's added, `pushFeedback()` fails silently and `sendFeedback()` falls back to the old `mailto:` link, so a message is never actually lost - just worth adding this rule promptly so testers' reports land where they're meant to. Same "sandbox network blocked" caveat as above: the graceful-failure/mailto-fallback path is what's actually been exercised, not a live Firestore write.

  - **Playtest stats need a fourth Firestore rule the owner still has to paste in (build 102)** - `pushStats()` in `js/cloud-save.js` writes one anonymous summary per tester (no name; counters, skill/gear/ladder numbers, deck family mix, Pebble ledger totals) to `stats/{uid}`, read only from the Firebase console. On by default, switch in Settings (`prefs.shareStats`). Same sandbox caveat as above: only the graceful-failure path has been exercised.
    ```
    match /stats/{uid} {
      allow write: if request.auth != null && request.auth.uid == uid;
      allow read: if false;
    }
    ```

  - **The town goal needs a fifth Firestore rule the owner still has to paste in (build 250)** - `communityPush()` / `communityFetch()` in `js/town-news.js` write one anonymous `{ n, goal, at }` per tester per week to `community/{week}/folks/{uid}` and read them all back to sum the other dreamers' shares. Gated on the anonymous-stats switch (`prefs.shareStats`). Without the rule it fails silently and the goal still works from your own share plus your neighbours'. Same sandbox caveat as above: only the graceful-failure path has been exercised.
    ```
    match /community/{week}/folks/{uid} {
      allow read: if request.auth != null;
      allow write: if request.auth != null && request.auth.uid == uid;
    }
    ```
    The Daily Rift board (build 259, js/daily-rift.js) uses the same rule with the doc id `rift-<day>`, so this one rule covers both.

**Account warning:** the machine's `gh` CLI also holds a work account, and that one is the *active* account. **Never** create repos or push personal projects with it. This repo's local git config already handles this:
- `user.name = Zenko`, `user.email = <id>+Zenko@users.noreply.github.com`
- a repo-local credential helper that asks for `gh auth token --user Zenko`

So `git push` from this folder always goes out as Zenko, even while the work account is active. Leave the work account active for `gh`. For `gh api` calls against this repo, prefix with `GH_TOKEN=$(gh auth token --user Zenko)`.

**Standing instruction from the owner: always publish.** When a batch of changes is finished and tested:
1. Add player-facing bullets to `PENDING_CHANGES` (see §5), bump `BUILD` in `js/build.js` by one (every publish needs this, even an internal-only change, so returning players' service workers pick up the new files), run `python3 scripts/check.py`, commit, and `git push origin main`.
2. Wait for Pages: `GH_TOKEN=$(gh auth token --user Zenko) gh api repos/Zenko/tile-rpg/pages/builds/latest --jq '.status + " " + .commit'` until it says `built` with your commit.
3. Tell the owner the link.

Don't publish broken or half-finished work.

Commit messages end with a `Co-Authored-By:` line for the Claude model doing the work.

## 3. How the owner likes to work

- They usually ask "what can we add?" and then say "**do them all**". Give a concrete, prioritised list grounded in the actual code, then build the whole batch, test it, and publish.
- **They have declined twice to hand-design the Quiet Harbor and Hollow Garden maps.** Those are still procedural placeholders (`proceduralMap()`). Don't redesign them unless asked.
- **Saves don't matter during testing.** They skipped a save export/import feature. Still, keep the existing habit of never crashing on an older save (see §6).
- They want playtesters to be able to find their way around, so every new system gets a first-time tip, a Town Guide entry and a `PENDING_CHANGES` bullet.
- The in-game Feedback and Report-a-bug buttons open an email to the owner (the address is in the `sendFeedback` code). They chose to keep it public.

## 5. Conventions to keep

- **Character system vocabulary.** Use these words in code, comments and docs. **Turntable**: the set of views of one character or item at 15 degree steps (the owner makes them with Illustrator's turntable; Alyn's is `assets/player/alyn/Alyn_360.svg`). **Facing**: the direction something looks (0 = towards you, 90 = to the screen's right); the town today walks four-way (down/right/up/left) and Alyn can *face* any of 24 angles (`sprTurnTo`, `playerLookAt`). **Rig**: one body type with its angles, layers and anchors (Original, Don and Alyn are three rigs; NPC bodies will be more). **Paper doll**: the layered dress-up side (hair and clothes colours, accessories) that sits on a rig. **Anchors** (mount points): where an accessory attaches (head top, face, head side, neck, back, hand); in head units a = her left, b = up, c = forward. Identifiers in the code keep their old names (`turn`, `plFace`, `plDeg`); only the words around them follow this list.
- **Beta releases.** Players see bundled releases ("Beta 1", "Beta 2", ...), not one note per change. Day to day, add a `{ t:'new'|'better'|'fixed', x:'...' }` bullet to `PENDING_CHANGES`; players never see it. When enough has built up (a handful of features), ask the owner, then move it into a new first entry of `RELEASES` (`id:'beta-N'`, `n:N`, real date, title, intro, `new`/`better`/`fixed` lists) and empty `PENDING_CHANGES`. A new release lights the Journal dot once; `CHANGELOG_ARCHIVE` is the collapsed "Before Beta" history and is never edited.
- **Comments** explain *why* in plain words, in the style of the existing ones. New systems get a banner comment with a short paragraph on how they work.
- **Save data before launch (owner, build 253).** The game is tested only by the owner until the reskin. **All save data will be reset** when the reskin is done and the real Beta with players begins, so until then nothing in a save needs protecting: card ids, item / quest / district ids, the order of `CARD_POOL` and `STORAGE_KEY` may all change during the reskin (update every use of an id: code, `CARD_FAMILY`, art file names, tests). Don't add save migrations for reskin changes. The "keep the id" / "append only" rules in this file and in `content/` apply again from the launch reset on. Changing `STORAGE_KEY` at launch is the simple way to start everyone fresh.
- **Reskinning: names live in js/game-config.js (build 251).** The game is meant to become a template for a full redesign, so the names players see (game title, currency, the player's title, districts, bosses, families, every named character) are values in `js/game-config.js`, and every sentence reads them: `` `${CAST.baker.name} laughs.` ``, `` `Harvest them in ${PLACES.square}` ``, `` `+${n} ${currencyName(n)}` `` (never `Ember${n > 1 ? 's' : ''}`). Titles in front of a name stay in the sentence ("the Atlas", "Madame Brume", "Maple's Bakery"). New dialogue must do the same: `python3 scripts/check.py` fails on a configured name typed into any string in `js/` (comments are fine; a line meaning the plain word, like the 'Ember' sleeve or the 'Fern' rug colour, ends with a `// names-ok: why` comment). In `index.html` a name is wrapped as `<span data-game="PLACES.square">El Umbral</span>` (the text is the fallback and check.py keeps it equal to the config; tooltips use `data-game-title="{GAME.currency.many} ..."`), and `manifest.json`'s name must equal `GAME.title`. `tests/game-config.test.js` renames everything through a patched config and fails if an old name shows anywhere. Changelogs are history and keep old names. Internal ids (`square`, `grove`, `pebbles`, card ids, `STORAGE_KEY`) never change with a reskin. Everything else the game says (cards, packs, buildings, dialogue, story, quests, tips) is in `content/` (build 252, see §4), so a full rewrite touches only `js/game-config.js`, `content/` and `assets/`; new tables of words or game data go there too.
  **Colours (build 253)** all live in `css/theme.css`, linked before the other six stylesheets. Section 1 is a palette, one variable per colour that rules use directly, named by hue and HSL lightness (`--c-amber-62`, `-aNN` = opacity) and the same in both themes. Section 2 holds every colour token moved there unchanged from the six files, with the same selectors, `@media` and relative order, so the cascade is identical: `:root` (dark, also the fallback), `:root[data-theme="light"]`, then biome, season, building, rarity and battle palettes in file order. The move was checked by comparing the computed colours of every element and `::before`/`::after` on 24 screens in both themes, old CSS against new (about 146,000 styles); the only differences were the same timing noise a new-against-new run shows (live sky tint, fading toasts). `check.py` now fails on a hex colour or a colour variable declared in any other `css/` file, and on a `var(--c-…)` that `theme.css` does not define, so a new rule picks or adds a palette entry (a colour that should differ between light and dark goes in as a token instead). **Colours outside CSS** are not in `theme.css`: rugs, wallpaper and furniture swatches in `content/items.js` and `js/home-room.js`, island and border colours in `js/world-map.js`, and everything drawn on canvas or WebGL (`js/town-render-weather.js`, `js/town-fx.js`, `js/battle-fx.js`, `js/player-fx.js`, `js/home-spirits.js`, `js/maps.js`, `js/pixi-particles.js`, `js/reveal-fx.js`, `js/battle-ui.js`), plus the drawn art in `scripts/art/` and `assets/`. **For Figma:** `python3 scripts/export-tokens.py` writes `design-tokens.json` (W3C design-tokens format: the palette, plus the `:root` theme tokens as `theme.dark` / `theme.light` modes) from `theme.css`; it is generated, so re-run it after editing `theme.css` and never edit the JSON.

- **Seeds, replays and the Node loader (build 132).** `BattleEngine.newGame(..., null, { seed })` makes a whole match reproducible: `makeRng(seed)` (mulberry32) drives the rules (`G.rng`: shuffles, mulligan) and a *separate* stream drives every AI decision (`G.aiRng`). Any new random draw in the rules goes on `G.rng`, any new AI choice on `G.aiRng`, never `Math.random` (the game itself still passes `Math.random` for normal play; only seeded matches use these). ## 6. State and saves

- Saved in `localStorage['quiet-commons-state-v4']`, with settings in `'quiet-commons-prefs'`. Each tester has their own save in their own browser.
- **Top-level `state` keys:** `ownedCards` (array of card ids; crafted variants are `base~p.guard`-style ids), `deck` (always the *active* deck), `deckSlots` and `activeDeckSlot`, `wins`, `currentDistrict`, `playerPos`, `districtData[key]` (NPCs, boss, items, spirits, decorations, crops, bugs, buildings state), `character` (emoji, colour, accessory, name, sleeve, title and unlocks), `companion` and `companionPos`, `sky`, `weather`, `decorationInventory`, and `progress`.
- **`state.progress`** holds almost everything else, and every system creates its own slice the first time it's used through an `xxxState()` function (for example `cupState()`, `museumState()`, `expedState()`, `mailState()`, `storyState()`, `foils()`). **Follow this pattern.** Never assume a field exists, because older saves won't have it.
- `loadState()` merges the save over the defaults. The `migrate*()` functions handle one-time upgrades.

## 7. How the systems fit together

- **Scenes (inside buildings).** `INTERIORS[id]` defines `title`, `who` (a string or function), `theme` and `greet` (a string or function), plus `actions`. Each action has a `kind` (`daily`, `advice`, `chest`, `memory`, `puzzle`, `minigame`, `oven`, `cook`, `deal`, `sleeves`, `seeds`, `mail`, `wings`, `exped`, and so on) and can have a `view()` that returns `{label, disabled}` for live buttons. Sub-menus use `scene.mode`. The cellar, the Festival Cup (the fountain) and the trading board (the Market sign) are special scenes rendered directly in `renderScene`. `sceneAction` routes in this order: leave, back, mini-game, prefixed ids (`dish:`, `wing:`, `exp-…`, `trade:`, …), special scenes, then action kinds.
- **Battles.** `startBattle(opponent)` reads optional fields on the opponent: `profile`, `deck`, `isBoss`, `dungeon`, `cup`, `challenge`, `puzzle` (a saved board), `signature`, `isRival` and `startSpirit`. `btShowResult` has one branch per kind, and `closeBattle` returns you to the right scene. District bosses get a twist through `bossTwistFor()`. The battle screen is the "Tabletop" layout (v1.58.0): a tilted `.table` (perspective on `.field`, `rotateX` on `.table`) holding both boards, Spirit as a conic-gradient ring (`--p` set in `btRenderBars`) around each portrait, and a fanned hand (`--rot`/`--dy` set per card in `btRenderHand`). Cards are played by **dragging** from the hand (`btStartDrag` → `btDragMove` → `btDragEnd` in `js/battle-ui.js`, pointer events, 8px threshold; a press that does not move is still the old tap-to-read, tap-again-to-play). The drop target is whatever is under the *ghost card's centre* (held above the fingertip): your slots for creatures (`btDoPlay`'s `slotIndex` moves the new card to that board index, which is cosmetic), the table for un-aimed spells, an enemy card for aimed spells. The Tabletop rules sit at the end of `css/*.css` and override the older flat-layout battle rules above them. **Table mats and decks (v1.59.0):** each side's row is `.trow` (a board plus a `.pile`); your row wears `mat-<id>` from `state.character.mat` (`MAT_OPTIONS` in `js/world-map.js`, bought in the Shop's Customize view and equipped in Player → Customize, same unlock pattern as emoji/colors, stored in `unlockedMats`). Piles and the opponent's hand are card backs (`btBackEl`, which wears your sleeve on your own); dealing flies a back with the Web Animations API (`btFlyBack`/`btDealOne`/`btDealOpening`), skipped when the device's reduced-motion setting or reduced-motion is on. During the opening deal the mulligan overlay waits until the deal finishes. **Battle fixes/effects (v1.61.0):** the board grid is `repeat(4, minmax(0, 1fr))` - never plain `1fr`, or a wide card stretches its column. Life is a `.sbar` under each name (updated in `btRenderBars`) as well as the portrait ring; `btSpiritFlash` flashes both. A ready card can also be *dragged* to attack (`btStartDrag(e, c, 'board')`, kind `'attack'`: drop on an enemy card, or anywhere above the enemy row for their Spirit; `#btAtkFace` is the tap equivalent). Effects (`btSlashFx`, `btShieldFx`, `btShake`, `btVignette`, `btSpellFx` with per-spell colours/kinds in `SPELL_FX`) are throwaway elements/WAAPI flights gated by `btMotionOk()`.
- **Mini-games.** Each `MINIGAMES` entry has `{house, icon, title, how, init, begin?, tap(st, value), render(st), scoreText, tiers or tierOf, lowerBetter?, pebbles?}`. Taps come from `data-mg` attributes on `pointerdown`. Timers are created with `miniEvery`/`miniAfter` so they're cleared automatically. `miniFinish(score)` awards the medal and prize, capped at 3 paid medals per game per day.
- **Places in town.** Town Square has Wren's cottage, the Reading Nook, the cellar, Maple's bakery, Fern's cottage, the player's cottage (top right, by the Nook), the fountain (Festival Cup and challenges) and the sign (weather board). Market Row has Pip, Clover, Saffron and Tock, the Card Museum (east hedge), the sign (trading board) and Lumen's Lantern Market (night only, tile 4,5). The Harbor has Tam's Net Loft and the Garden has Iris's Glasshouse - one building each, placed at a fixed spot inside `proceduralMap()` (see §4/§10) rather than by hand-designing the rest of the layout.

## 8. Testing (how every change so far was checked)

**First, always:** `python3 scripts/check.py` - syntax of every file, no duplicate element ids, no `getElementById('x')` for an id that is not in index.html, valid `RELEASES`/`PENDING_CHANGES`, no top-level name declared in two files (all scripts share one global scope: the later file silently replaces the earlier one, which once emptied the Cards Index when a Journal function reused `renderAlmanac`), every `<script src>` exists.

**Tests (`tests/`).** `node tests/run.js [filter]` runs every `tests/*.test.js` in headless Chromium (Playwright; `npm i -D playwright` once). Each test is `async (page, assert)`, gets a fresh game with first-time tips off and overlays hidden, and fails on any page or console error. Covered: boot and tabs, the battle engine (60 AI games), who-goes-first, Draft Run, fishing silhouettes, Cards, Rewards, Character, Journal, old/hostile saves, and data consistency (guide, cards, sets, quests). Add a `<area>.test.js` with each new screen. `.github/workflows/check.yml` runs `scripts/check.py` and these tests on every push, so a red check on GitHub means something broke before or after Pages published.

Every change was checked with **Playwright** driving the real page in headless Chromium: open the file, run scripted play, and fail on any `pageerror` or console error. A Chromium build is cached at `~/Library/Caches/ms-playwright`. Install the library in a scratch folder with `npm i playwright`, not in this repo. A minimal runner:

```js
// run.js - usage: node run.js test.js   (test.js exports async (page, log) => {})
const { chromium } = require('playwright'), path = require('path');
(async () => {
  const b = await chromium.launch(), page = await (await b.newContext({ viewport: { width: 400, height: 860 } })).newPage();

```

**Both renderers are tested.** `node tests/run.js` runs on the WebGL town (the default); `TILE_RENDERER=dom node tests/run.js` runs the whole suite on the classic DOM town (the fallback path); CI runs both. `tests/town-gl.test.js` covers the WebGL town itself (small DOM, camera sync between ground and entities, tree overhangs, placement and Hide and Seek glow, theme recolour, district change, fallback, `?renderer=dom`) and skips itself when there is no WebGL. `DEBUG_NAV=1 node tests/run.js <name>` logs page navigation, frame, crash and console events while a test runs. **A walking test must empty the district first** (`data.npcs.length = 0; data.boss = null; data.items = []; data.spirits = []`): a wandering or randomly placed neighbour on the route makes `findPath` return null or the walk stop without calling its callback, which looks like a flaky test (and once looked like a navigation error).

**Frame-time benchmark.** `node scripts/perf-town.js [--renderer=dom|canvas|pixi] [--seconds=10] [--only="rain, night 4x"] [--hide=weather|sky|tiles|all] [--map=big200]` walks the player across Town Square under clear/rain/snow and CPU throttling and prints frame gaps, main-thread busy time and the **steps actually walked** (a run with 0 steps is idle and its numbers mean nothing; the benchmark empties the district first so a neighbour cannot block the route). The default renderer is the WebGL town, `--renderer=dom` the classic one, `--renderer=pixi` the standalone lab. Headless desktop Chromium with software-rendered WebGL: use it for before/after on one machine, repeat each case, treat frame gaps as rough (main-thread busy time is steadier) and never read GPU-bound frame rates from it. Early notes (taken before the idle-run flaw was found, so only the direction is reliable): the rain layer was the most consistent cost; a 2x weather canvas was slower than the DOM drops, 1x about level.

Useful habits:
- **Syntax check:** `for f in js/*.js assets/sprites.js; do node --check "$f"; done` - each file must be independently valid, since browsers parse each `<script src>` as its own unit (unlike the old single `<script>` block).

- **Animation rules learned from a long chain of player "glitch" reports (v1.21.0-v1.25.0 - full incident history in `HANDOFF-HISTORY.md`):**
  - When gating an infinite CSS animation (not just its opacity) behind a class, prefer "always animate, gate opacity" (the pattern every weather layer but the original lightning used). If the animation itself must be turned on/off, do it explicitly in JS with `element.style.animation` - a class-match toggle alone can leave it "stuck" running on real mobile browsers even after the class stops matching.
  - Always animate `transform`/`opacity`, never `top`/`left`/`margin`/`width`/`height`, for any looping animation running across many elements (e.g. rain/snow). Animating a layout property forces a layout recompute every frame per element - expensive enough on a mid-range phone to drop or tear frames, and a torn frame can visibly corrupt unrelated parts of the same paint (not just the animated layer), which is what made this bug look like several unrelated glitches.
  - Avoid `filter: blur()` on anything animated that stays visible for a long stretch (a GPU-compositing cost invisible in desktop testing).
  - This game is tested almost entirely in desktop headless Chromium (see §8); a real device can behave differently for anything animation/filter/transform-heavy. When a player reports a visual glitch that can't be reproduced in the usual harness, suspect a class-gated or layout-animating CSS rule before assuming the JS logic is at fault - especially if repeated "fixes" don't fully resolve it and the common thread across reports is a system (e.g. "happens when it's raining") rather than one element.
- **Tearing on phones, round three (v1.78.0, from a screen recording).** Causes found, all now removed - don't reintroduce them: (1) `applySky()` re-set `--sky-color`/`--sky-tint` on every town tick while `.town-sky` had a 3s `transition` on `background`, so the full-viewport overlay was *repainting almost permanently* (it now writes a property only when its value changed, and only `opacity` transitions); (2) `mix-blend-mode` (multiply/soft-light on the sky, screen on the player glow) forces whole-map re-compositing; (3) `backdrop-filter` on the always-visible glass chrome (HUD, dock, ambient line, radar button) and on overlay scrims re-blurs the animating map each frame - it is now disabled globally at the end of css/style.css, so never add one; (4) `filter: drop-shadow` (and an animated `filter` in `boss-aura`) on animated map characters - use `text-shadow` on the emoji span instead; (5) the player-light mask on the sky (`updateNightHole`) is only updated while some night darkening is actually showing. If tearing is reported again, record the screen and check these first.
- **`renderTown()`/`renderEntities()` must not fight an in-flight animation - this bit twice.** `startWalk()`'s `step()` animates the camera and player over `STEP_MS` (170ms) by setting `transition: transform 140ms linear` (etc.) then a new transform/position. Any *other* trigger of `renderTown()` landing mid-step - the periodic 2s town tick, an item pickup, a wander sync, literally anything - used to call `positionPlayer(false)`/`updateCamera(false)` unconditionally, which sets `transition: none` and re-applies the exact same final transform: since the transition is now off, the browser snaps instantly to that endpoint instead of finishing the glide, visible as a brief flash/jump (confirmed by capturing `townWorld.style` mid-step in Playwright: `transition` and `transform` were both silently overwritten). Fixed by skipping that resync while `playerEl.classList.contains('walking')` - `step()` itself already keeps position/camera in sync every 140ms, so nothing is lost.
  - **The same bug existed one level down, for NPCs and spirits.** `renderEntities()` used to destroy and recreate *every* non-player entity from scratch on every call, including ones nothing changed about. Spirits drift via a 500ms CSS transition (`.ent.spirit`) and `moveFighter()` (js/neighbors-bosses.js) animates NPCs the same way - mutating `--x`/`--y` on the *existing* element so the transition glides. A `renderTown()` landing mid-drift destroyed that element and replaced it with a fresh one already at the final position, snapping the glide instantly and restarting the idle bob's animation phase. Fixed by keeping `entityElsById`/`spiritElsById` (see §4's town-render-weather.js entry) across renders and reusing the existing element by id - only updating its position/name - instead of removing and recreating it; only entities with no id-based identity (props, decorations, crops, items, the chest, the companion, the lantern vendor, bugs, the mail flag) still get fully rebuilt each render, since none of them have an in-flight transition to protect.
  - **When anything reaches into camera/player/entity positioning from outside its own animation loop (a walk step, a wander tick, a drift), check whether that loop already owns an in-flight transition on the same element first, or a redundant resync will cut it short.**
  - **The reuse fix above then caused its own bug: duplicate NPCs/bosses on screen (reported by a player - two "Rook"s, two of the district boss, side by side).** The reuse condition originally required an *exact* `className` match (`e.className === 'ent ' + cls`) before reusing an element. But one-shot classes added elsewhere outside `renderEntities()` - `npc-arrive` on arrival, `boss-appear-cycle`/`boss-vanish` on the boss's 30-min cycle (js/neighbors-bosses.js) - permanently change that element's `className`, so it never matches again: every later render fell into the "create new" branch *without removing the stale old element* (its id was still in `liveFighterIds`, so the end-of-loop cleanup left it alone), leaving both the old and new element on screen indefinitely. Only Rook and the boss are hit because they're the only entities that ever gain one of these transient classes - ordinary villagers never do, which is why they never duplicated. Fixed by dropping the `className` equality gate entirely (always reuse an existing, connected element by id) and only toggling the one class that can legitimately change identity (`rival`) via `classList.toggle`, leaving any transient animation class alone rather than overwriting the whole `className` (which would have re-introduced the interrupted-animation bug from the point above). **When reusing a DOM element by id across renders, never gate reuse on its full `className` matching exactly - something outside your control may have added a one-shot class to it. Toggle only the specific class(es) your own code owns.**
- **Cross-file load order matters for top-level references, but not for anything inside a function.** All `js/*.js` files share one global scope (see §1), loaded in the order in `index.html`. A function can freely call another function from *any* file, in *any* order, because by the time a user can click anything, every file has already finished loading. The one real trap: a top-level `const X = { ... }` or `[ ... ]` that references another function or const **by bare identifier** (not wrapped in `() => …`) is evaluated immediately, at parse time - if that identifier's file hasn't loaded yet, it throws and silently kills the rest of that script file (later `const`s in the *same* file never get created either, which shows up as confusing "X is not defined" errors somewhere else entirely). This is exactly what broke `INTERIORS` the first time `houses-and-cellar.js` was split out (`view: puzzleView` needed `puzzle-memory-minigames.js`, which loads later) - fixed by wrapping it lazily: `view: () => puzzleView()`. **When adding a new top-level object/array that reaches for a function or const from another file, always wrap it in an arrow function** (`() => …`) rather than passing the bare identifier, and this whole class of bug can't happen regardless of load order.
